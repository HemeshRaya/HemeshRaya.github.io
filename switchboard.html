The problem

Clinics and salons want a WhatsApp assistant that books appointments, sends reminders and runs campaigns. Building one per client is slow, and a single bug could show one customer's data to another.

What I built

A single engine serves every client. Each business is described by a config spec, and PostgreSQL Row-Level Security makes sure a tenant can only ever see its own rows.

Features

What it does

AI chat on WhatsApp

Answers customers using the business's own information, in a conversational flow.

Native booking

Customers book appointments inside the chat, with booking-conflict checks.

Reminders

A worker process detects and sends reminders on its own schedule.

Campaigns

Approved-template campaigns to leads, with opt-out handling.

Prescription relay

Append-only records: a follow-up visit is a new row, never an overwrite.

Config-only onboarding

A clinic and a salon share one schema. A YAML spec adds a new client.

Design decisions

Choices that matter

Isolation lives in the database

Row-Level Security is structural, not a convention. A dedicated runtime role cannot bypass it, and automated tests verify it.

One engine, config-driven tenants

Prompt content and capability flags differ per client. Application code does not.

Separate web and worker processes

A burst of outbound campaign sends never adds latency to a live chat reply.

No websocket

WhatsApp Cloud API is HTTP-only: inbound by webhook, outbound through the Graph API.

Nothing important is silently lost

Chat transcripts are permanent, and prescriptions are append-only.
